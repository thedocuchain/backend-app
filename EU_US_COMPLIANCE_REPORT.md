# Соответствие стандартам EU/US — аудит backend-app

Дата: 2026-08-03. Scope: весь `src/` backend-app (NestJS), docker-compose, ansible.
Сервис: подписание документов + blockchain-анкоринг + аккаунты + Stripe-биллинг.

## Вердикт одной строкой

Продукт **не соответствует** ключевым требованиям GDPR (права субъектов, согласие, retention) и **не дотягивает** даже до «простой» электронной подписи в смысле юридической доказуемости (eIDAS AES — не выполнен, ESIGN — частичное выполнение). PCI-периметр чистый. Есть несколько критичных security-проблем, которые одновременно являются нарушением GDPR Art. 32 (security of processing) и напрямую угрожают бизнесу.

## Матрица соответствия

| Стандарт | Статус | Кратко |
|---|---|---|
| **GDPR** (EU 2016/679) | ❌ не соответствует | нет удаления/экспорта данных (Art. 17/20), нет записи согласия, нет retention, контент документов уходит в Vertex AI без consent |
| **eIDAS** (910/2014, Art. 26 AES) | ❌ не соответствует | подпись — не AES: нет криптографической привязки подписи к документу и подписанту, нет контроля единственности (bearer-ссылка), целостность не обеспечивается |

| **CCPA/CPRA** (California) | ❌ не соответствует | право на удаление и «right to know» технически невыполнимы |
| **CAN-SPAM** (US email) | ⚠️ частично | нет физ. адреса в письмах, unsubscribe требует логина, промо-блок Trustpilot в reminder-письмах |
| **PCI DSS** | ✅ OK (SAQ-A) | карточные данные не трогаем (только Stripe Checkout/Portal), webhook верифицируется |
| **EU AI Act** (Art. 50) | ⚠️ частично | AI-раскрытие только на фронте (не проверяемо с API), opt-in на отправку документа в Google отсутствует |
| **NIST 800-63B / OWASP ASVS** (auth) | ⚠️ частично | scrypt+соль OK, сессии с server-side отзывом OK; но нет rate limiting, cookie httpOnly:false, OAuth-уязвимости |

## КРИТИЧНОЕ (P0) — чинить в первую очередь

### 1. Захват аккаунта через Google OAuth (account takeover)
`account-auth.service.ts:155-171` — `loginWithGoogle` ищет аккаунт по `[{googleId}, {email}]` и мёржит `googleId` в найденный аккаунт. Атака: злоумышленник регистрируется с email жертвы (`register`, строки 58-76, не требует верификации для создания строки) и задаёт свой пароль; когда жертва впервые входит через Google — её `googleId` и `emailVerifiedAt` дописываются в строку атакующего, после чего атакующий входит по своему паролю в аккаунт жертвы со всеми её документами.
**Фикс:** никогда не мёржить по email; при конфликте — требовать явный линкинг из авторизованной сессии.

### 2. Анонимный mass assignment: подмена подписанта чужого документа
`users.controller.ts:11-19` — `PATCH /v1/users/:id` без какой-либо авторизации; `users.service.ts:31` — `save({...user, ...updateUserDto})`. Глобальный `ValidationPipe()` без `whitelist` (`main.ts:29`) не вырезает лишние поля. Зная UUID участника (он утекает через `GET /v1/documents/:id` без авторизации), можно подменить signer'у email на свой и подписать за него, поменять `role`/`isInitiator`/`documentId`.
Тот же вектор через `PATCH /v1/documents/:id` (анонимный, `documents.controller.ts:84-92`) — можно переоткрыть подписанный документ, добавить участников, переименовать, сменить chain. Бонус: валидация роли сломана — `@Contains(UserRoles.SIGNER || UserRoles.WATCHER)` вычисляется в `@Contains('signer')` (`create-user.dto.ts:80`).
**Фикс:** `whitelist: true, forbidNonWhitelisted: true` в ValidationPipe, auth-guard на legacy-эндпоинты (или удалить их), запрет модификации документов в `COMPLETED`/`BLOCKCHAINED`.

### 3. Нет rate limiting нигде (после удаления reCAPTCHA)
`grep -rniE 'throttl|rate.?limit|captcha' src/` — только лимиты verification-кодов. Login, register, resend-code, notify (анонимная рассылка писем всем подписантам), загрузка 50MB файлов, фидбек → Telegram — всё без ограничений. Брутфорс паролей и email-бомбинг через Mandrill ничем не сдерживаются.
**Фикс:** `@nestjs/throttler` глобально + жёсткие лимиты на `/v1/auth/*` и `:id/notify`; рассмотреть Turnstile/hCaptcha на регистрацию/логин.

### 4. Анонимное скачивание любого документа по UUID
`GET /v1/documents/:id/download` (`documents.controller.ts:103-110`) возвращает presigned URL на подписанный PDF без авторизации; `GET /v1/documents/:id` отдаёт имена, email, IP и user-agent всех подписантов. UUID — единственная защита. Это прямое нарушение GDPR Art. 5(1)(f)/32 и потенциальный инцидент с утечкой контрактных данных.
**Фикс:** авторизация на чтение/скачивание; публичный доступ — только по верификационной ссылке с токеном.

### 5. Сессионный токен доступен JS + CORS без ограничений
`google-auth.controller.ts:67-73` — cookie `httpOnly: false` (30-дневный токен читается любым XSS); `main.ts:37` — `enableCors()` без origin-листа (`*`); WebSocket-гейтвей тоже `origin: '*'` (`events.gateway.ts:10-14`). Любой XSS на любом origin → угон аккаунта.
**Фикс:** `httpOnly: true`, CORS allowlist на наши домены.

## GDPR — детальные пробелы

| Требование | Статус | Детали |
|---|---|---|
| Art. 17 (удаление) | ❌ | Нет эндпоинта удаления аккаунта вообще; единственный `@Delete` в коде — отзыв сессии. Данные не удаляются никогда. |
| Art. 20 (портабельность) | ❌ | Нет экспорта (JSON + PDF). |
| Art. 6/7 (согласие) | ❌ | В `src/` ноль упоминаний consent; при регистрации ToS/privacy не запрашиваются; Google-signup создаёт аккаунт молча. Хуже: для watcher'ов `agreedWithPolicy: true` пишется хардкодом без спроса (`documents.service.ts:804`). |
| Art. 5(1)(e) (retention) | ❌ | Нет ни одной cleanup-джобы: истёкшие verification-коды, отозванные сессии, blacklist, файлы — всё хранится вечно. `FileStorageService.delete()` не вызывается никем. |
| Art. 28 (процессоры) / трансферы | ⚠️ | Vertex AI получает **полный контент** документов, endpoint `location: 'global'` (Google роутит инференс куда угодно); region GCS-бакета в коде не задан; Telegram получает name/email/текст support-запросов без DPA. Реестра обработчиков нет. |
| Art. 5(1)(d)/минимизация | ⚠️ | В access-логи пишется IP + полный query string, включая `?token=` JWT (`logger.middleware.ts:28-30`); `trust proxy: true` позволяет подделывать IP через X-Forwarded-For. |
| Art. 21 / ePrivacy | ⚠️ | Unsubscribe только для reminders и только после логина; `List-Unsubscribe` заголовков нет. |
| Art. 33/34 (breach notification) | ❌ | Нет ни детекции, ни процесса уведомления за 72 часа. |
| Marketing-письма | ⚠️ | В reminder-письмах промо-блок Trustpilot без адреса/ансабскрайба — письмо становится «коммерческим» по CAN-SPAM. |

Отдельно: email-шаблон утверждает *"Your document is securely stored on the blockchain forever"* (`email.util.ts:154`) — это неправда (в блокчейне только хеш, файл в GCS) и это противоречит будущему праву на удаление. Исправить копирайт.

## eIDAS / ESIGN — детально

Подпись сейчас — clickwrap + bearer-ссылка из письма + хеш в блокчейн постфактум. Оценка по Art. 26 eIDAS:

- **(a) уникальная связь с подписантом** — слабая: только DB-связка JWT→User, криптографии нет;
- **(b) идентификация** — частичная: email + имя, введённое инициатором; внешних подписантов никто не верифицирует;
- **(c) sole control** — не выполнено: подпись = обладание ссылкой из письма (2 дня жизни, переотправляется в каждом notify, старые токены не отзываются, OTP при подписании нет);
- **(d) обнаружимость изменений** — не выполнена на практике (см. дефекты ниже).

**Дефекты, ломающие доказательность:**
1. **Хеш не совпадает с файлом.** Хеш считается с неподписанного tx-hash буфера (`documents.service.ts:510-514`), затем `stampTransactionHash` рисует tx-hash в PDF и заменяет хранимый файл (`documents.service.ts:658-671`). Хеш из скачанного файла НЕ совпадёт с ончейн-записью. Это убивает весь смысл анкоринга.
2. **Промежуточные версии уничтожаются** (`replaceFile` на каждой подписи) — не доказать, что видел каждый подписант.
3. **`signDate` присылается клиентом** (`sign-document.dto.ts:49-54`) и хранится как есть; доверенного времени нет (ни TSA, ни хотя бы server-side времени в записи подписи).
4. **Audit trail редактируемый и скудный**: обычная таблица без хеш-цепочки, всего 2 типа событий (`audit-logs.service.ts:13-25`).
5. **Флаги согласия декоративные**: `sign()` не проверяет `agreedWithPolicy === true` (`documents.service.ts:536-542`); подписант может подписать с `false`. Нет записи версии/текста disclosure.
6. **Нет decline/revoke/void** ни для подписи, ни для документа.
7. **Анкоринг падает молча**: catch только логирует (`documents.service.ts:653-655`), документ остаётся `COMPLETED` с `blockchainTransaction: null`; при неудаче анкоринга письмо о завершении вообще не отправляется (`if (transactionHash)` на `:620`). Bitcoin/DigiByte — broadcast без ожидания подтверждений. Monad в конфиге — **testnet** (`blockchain.config.ts:54-65`).
8. В PDF нет криптографического слепка (PAdES/CMS) — только нарисованная картинка.

Для US: ESIGN §101(c) consumer consent (disclosure + affirmative consent + демонстрация доступа к e-записям) отсутствует полностью; для B2B-сценариев это менее критично, для consumer-документов — критично.

Если цель — продавать подпись как юридически сильную в EU, нужен другой класс архитектуры (OTP/ключ подписанта на церемонии, PAdES, хеш-цепочка аудита, RFC 3161 timestamp). Текущую архитектуру «докрутить» до AES нельзя.

## Payments / Email / AI

- **PCI**: ✅ только Stripe Checkout/Portal, хранятся лишь идентификаторы, webhook верифицируется (`billing.service.ts:161-169`). Остаёмся в SAQ-A.
- **CAN-SPAM**: нет юрлица+физ. адреса в футере писем; unsubscribe требует логина; нет `List-Unsubscribe`.
- **AI review**: полный PDF уходит в Vertex без opt-in и без серверного disclosure (в промпте написано «интерфейс уже показывает дисклеймер» — на бэке не проверяется); любой участник документа может отправить общий документ в Google без ведома остальных; биллинг-гейт fail-open (`if (!billingEnabled) return` — при сбое конфига AI становится бесплатным).
- **Support → Telegram**: персональные данные тикетов уходят в мессенджер без DPA и без уведомления пользователя; публичный эндпоинт фидбека без auth и лимитов.

## Что уже хорошо (зафиксировать, не сломать)

- Stripe и Mandrill webhook'и верифицируются корректно (raw body + signature / HMAC+timingSafeEqual).
- Пароли: scrypt + соль + timingSafeEqual (NIST-приемлемо).
- Сессии: server-side строки в БД с проверкой на каждый запрос и отзывом; смена/сброс пароля требуют текущий пароль/код и отзывают остальные сессии.
- SQL только параметризованный; нет user-controlled SSRF и path traversal; файлы под UUID-ключами.
- Swagger выключен в проде; helmet включен; секреты никогда не коммитились (проверено по истории git).
- Открытие/клик трекинг в письмах выключен.

## План работ (приоритизированный)

**P0 — безопасность (недели 1-2):**
1. Фикс Google OAuth merge (убрать слияние по email).
2. `whitelist`/`forbidNonWhitelisted` в ValidationPipe + `@Type` для nested DTO + auth на `PATCH /users/:id`, `PATCH /documents/:id` + запрет модификации завершённых документов.
3. Throttler на auth-эндпоинты, notify, upload, feedback.
4. Авторизация на download/read документов; убрать публичную отдачу PII участников.
5. `httpOnly: true` cookie + CORS allowlist.

**P1 — юридическая значимость подписи (недели 2-4):**
6. Хеш после штамповки (или хранить оба файла и оба хеша); сохранение промежуточных версий.
7. Серверный enforcement consent-флагов + запись версии disclosure + серверное время подписи вместо клиентского.
8. Хеш-цепочка в audit-logs + новые типы событий; верификационный эндпоинт (пересчёт хеша + подтверждение транзакции).
9. Очередь ретраев анкоринга; письмо о завершении независимо от анкоринга; убрать/пометить Monad testnet; подтверждения для UTXO-цепей.
10. Отзыв старых signing-токенов при переотправке; OTP при подписании (есть готовый `VerificationService`).

**P1 — GDPR ядро (недели 3-5):**
11. `DELETE /v1/account` (каскад: сессии, коды, Stripe, анонимизация/удаление документов) и `GET /v1/account/export`.
12. Consent-чекбоксы при регистрации + `(agreedAt, policyVersion)` в аккаунте; убрать хардкод флагов у watcher'ов.
13. Retention-джоба: истёкшие коды, старые отозванные сессии, анонимные драфты.
14. Убрать IP/query-токены из access-логов; trust proxy на диапазоны Cloudflare.
15. Пин `VERTEX_AI_LOCATION` (EU-регион) + disclosure/opt-in перед AI-review; реестр обработчиков (Art. 30) и Vertex/GCS/Mandrill/Telegram в privacy policy; проверить регион GCS-бакета.

**P2 — email/прочее:**
16. Адрес юрлица в футер писем; подписанный токен для one-click unsubscribe без логина; `List-Unsubscribe` заголовки.
17. Уведомление пользователей, что support идёт через Telegram (или перенос на processor с DPA).
18. `.env` в `.dockerignore`; убрать `--allow-unauthenticated` apt; fail-closed биллинг-гейт.
19. Breach-response процесс + алертинг security-событий (Art. 33).
20. DPIA (изображения подписей ≈ биометрия, IP, контент PDF) + формулировка warranty в ToS на email'ы третьих лиц, предоставляемые инициатором.
